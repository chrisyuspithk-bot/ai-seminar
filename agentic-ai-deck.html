Part 2 · Agentic AI 與 LLM 的根本差異

從「會說話」到「會做事」

過去幾年，我們對 AI 的印象大多停留在聊天機器人：你問問題，它給答案；你要求寫文章，它整理內容。但到了 2026 年，AI 不再只是被動回應指令，而是開始主動替人完成工作。

生成式 AI

幫你編故事、寫詩、畫圖——它產出的是「內容」。

Agentic AI

會在世界中採取行動的 AI——行動可以是物理的（機器人操作），也可以是數位的（幫你訂機票）。

Part 2 · Agentic AI 與 LLM 的根本差異

四層智能躍遷：像四級台階

這個框架把 AI 系統的能力分成四層，一層比一層更接近「自主完成工作」。

LAYER 1

LLM

解決「會不會說」：語言理解、內容生成、邏輯推理。是 AI 系統的認知基礎。

LAYER 2

RAG

解決「有沒有依據」：檢索外部知識庫，讓回答從「流暢」走向「可信」。

LAYER 3

AI Agent

解決「能不能做事」：拆解任務、調用工具、規劃步驟，從回答走向行動。

LAYER 4

Agentic AI

解決「能不能協同」：多個智能體分工、共享記憶、形成反饋閉環。

一句話貫穿LLM 是語言引擎、RAG 是知識底座、AI Agent 是任務執行單元、Agentic AI 是組織協同系統。

Part 2 · 一句話記住

LLM 是智能的語言引擎，RAG 是智能的知識底座，AI Agent 是智能的任務執行單元，而 Agentic AI 是智能的組織協同系統。

每一層都不是取代，而是往上疊加。你不可能跳過 LLM 直接得到 Agentic AI。

Part 3 · Agent Swarm 多代理協作

如果一個 Agent 不夠強，
為什麼不訓練一個更強的？

因為現實世界的複雜任務，需要的專業知識遠超單一模型的能力邊界。有些模型擅長數學推理、有些擅長程式工程、有些擅長安全分析。與其訓練一個「全能模型」，不如讓多個專責模型協同工作。

Agent Swarm 的核心思想智能不在節點，而在關係。

Part 3 · 戰略意義

不只是「向上擴展」，
還要「向外擴展」

月之暗面把方向概括為兩件事：更大的模型，以及更多的 Agent。這聽起來像工程決策，實際上是一個範式宣言——人工智能正在從「單體大腦」走向「思維社會」。

明斯基《心智社會》(1986)我們感受到的那個統一、連貫的「自我」，其實是由大量能力有限的認知智能體共同構成。智能不僅存在於每個組件之中，更存在於這些組件的組織方式之中。

Part 3 · 日本案例：Sakana AI

Sakana Fugu：AI 的「總指揮」

Sakana AI 是 2023 年成立的日本 AI 獨角獸，由 Transformer 論文第五作者 Llion Jones 聯合創辦。它從一開始就不訓練更大的單一模型，而是用「進化」的方式，讓小模型組合出堪比大模型的能力。

Fugu 是什麼

2026 年 6 月發布的編排器模型。Fugu 在日文是河豚，設計理念是用多個「小魚」匯聚成一隻「大河豚」。

關鍵特性

Fugu 不會自己回答問題——它會調用世界上各種模型來完成任務。像一個總指揮，根據任務挑選最合適的模型。

Part 3 · 日本案例：Sakana AI

Fugu 的四個基礎機制

MECH 1

識別問題類型

判斷是程式、數學、推理、資訊檢索、科學分析還是多模態任務。

MECH 2

選擇 worker 模型

不同模型在不同任務上差異很大，Fugu 學會「什麼問題派給誰」。

MECH 3

拆解任務

把複雜問題分解成可處理的子任務。

MECH 4

校驗與綜合

檢查各模型輸出的品質，綜合得到最終答案。

核心精神它不訓練一個更強的基座去解題，而是判斷「這道題該交給誰、怎麼拆、如何驗證」。答案品質超過多個單一模型獨立作答的結果。

Part 4 · 框架層：開發者如何構建 Agent

Google ADK（Agent Development Kit）

Google 在 2025 年 4 月 Cloud NEXT 發布的開源框架，目標是簡化 Agent 與多 Agent 系統的全棧端到端開發。

特色 1

Multi-Agent by Design

以層級結構組合多個專責 Agent，實現協調與委派。

特色 2

豐富模型生態

支援 Gemini、Vertex AI Model Garden，並透過 LiteLLM 整合 Anthropic、Meta、Mistral。

特色 3

豐富工具生態

內建工具、MCP 工具、第三方函式庫，甚至能把其他 Agent 當工具用。

特色 4

內建評估

系統性評估最終回應品質，以及逐步執行的軌跡。

值得注意ADK 就是 Google 自家產品 Agentspace 與 Customer Engagement Suite 所使用的框架。

Part 4 · 框架層：開發者如何構建 Agent

LangGraph：把工作流畫成一張圖

LangChain 團隊開發，用於構建有狀態的、多參與者的 LLM 應用。核心思想是把 Agent 工作流程抽象成有向圖，用節點和邊定義執行步驟與邏輯流。

CONCEPT 1

StateGraph

共享的、不斷演變的狀態，實現記憶功能。

CONCEPT 2

Node

代表一個步驟、一個 Agent 或一個工具。

CONCEPT 3

Edge

代表節點之間的轉換條件。

CONCEPT 4

Persistence

內建持久化層，支持記憶、中斷恢復、人工參與控制。

實際用戶LinkedIn、Uber、Klarna、GitLab 等。

環境準備

請先確認你的 Mac 滿足以下條件，並準備一組可用的 LLM API Key。

Part 6 · OpenHands Cloud 教學

OpenHands 的架構解析

理解它的架構，你才知道它的能力邊界在哪裡。

核心

LLM · Agent

LLM 代理所有模型互動；Agent 定義行為邏輯；AgentController 控制執行流程。

環境

Runtime · Sandbox

Runtime 提供執行環境，Sandbox 隔離執行，確保安全。

服務

Server

透過 HTTP 代理 OpenHands 會話，驅動前端。

骨幹

EventStream

所有組件之間的通訊，都透過 EventStream 傳遞訊息。

一句話OpenHands 給 LLM 配備完整的開發環境：終端、檔案系統、編輯器與瀏覽器——這是一個閉環回饋系統，不只生成程式碼，還能驗證程式碼是否正確執行。

Prompt 請用 Python Flask 建立一個待辦事項 Web App，要求：1）可以新增、編輯、刪除待辦事項；2）支援標記完成／未完成；3）使用 SQLite 儲存資料；4）前端用簡單的 HTML + CSS，不要用框架；5）寫一個 README.md 說明如何運行；6）寫測試。完成後啟動伺服器，確認可以正常運行。

Part 6 · 觀察 Agent 的工作流程

從規劃到交付，六個階段

  1. 規劃：識別這是 Web App 開發任務，制定執行計劃，將問題分解成可執行步驟。
  2. 環境準備：檢查環境、安裝依賴（Flask、SQLite 等），建立專案目錄結構。
  3. 程式碼編寫：依序創建 app.py、models.py、templates/index.html、static/style.css、test_app.py、README.md。
  4. 測試與除錯：執行測試，發現錯誤就自動修正並重新測試——一個自我迭代的過程。
  5. 啟動與驗證：啟動 Flask 伺服器，確認應用可以正常訪問。
  6. 交付：總結完成的工作，告訴你專案結構與如何運行。

Part 6 · OpenHands 的關鍵設計原則

這不只是生成程式碼
而是完成一整個開發任務

原則 1

Sandbox 隔離

所有操作都在隔離的沙盒執行，不影響你的本地系統。

原則 2

EventStream 驅動

所有組件透過 EventStream 傳遞訊息，具備良好的可觀測性與可擴展性。

原則 3

模型無關

可隨時切換底層 LLM，不需改變 Agent 的行為邏輯。

原則 4

原生沙盒化

整合沙盒執行、生命週期控制、多 LLM 路由與內建安全分析。
