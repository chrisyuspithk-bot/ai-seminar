Part 1 · LLM 基礎概念

ChatGPT 到底在「做」什麼？

它其實不是「查資料」，而是在做下一個詞的機率預測。這個概念，是理解所有 LLM 行為的起點。

STEP 1

接收輸入

你打的字會被切成 token（詞元）。Token 不是字也不是詞。英文約 1 token = 0.75 個單字；中文約 1 個字 = 1 到 2 個 token。

STEP 2

計算機率

模型根據訓練時學到的數千億參數，計算「下一個 token 最可能是什麼」。

STEP 3

逐個生成

一個 token、一個 token 地吐出來，直到生成結束。

重點一句話問它「台灣最高的山是哪座」，它不是去查資料庫，而是算出「台灣最高的山」後面最常接什麼詞。LLM 是機率機器，不是知識庫。
Part 1 · LLM 基礎概念02 / 35

Part 1 · LLM 基礎概念

Transformer 與自注意力機制

支撐這一切的架構叫做 Transformer，最核心的技術是 Self-Attention —— 讓模型生成每一個詞時，能「回頭看」序列中的所有詞，判斷哪些最相關。

小明把蘋果給了小華，因為他很餓。

問你：「他」指的是誰？我們靠上下文判斷。Transformer 的注意力機制，也在做同一件事。

注意力的本質

每個詞都對其他詞算一個相關分數，分數高的，對當前生成的影響就大。

為什麼是突破

它讓模型能平行處理整個序列，不再一個字一個字慢慢讀，訓練規模因此爆炸成長。

所以才有 LLM

沒有注意力機制，就沒有後來能讀完整本書、還能記住前文的大語言模型。

參數規模：4B、7B、70B 的意義

B 代表 Billion（十億），所以 7B 就是 70 億個參數。參數越多，模型理論上越聰明，但需要的硬體資源也越多。

4B

輕量級

40 億參數。一般筆電、甚至 8GB RAM 的機器就有機會跑得動，適合當入門練手。

7B

甜蜜點

70 億參數。品質與資源的平衡，是目前本地部署最主流的規模。

70B

重裝旗艦

700 億參數。推理能力明顯更強，但通常需要高階 GPU 或大容量 VRAM。

實務結論LM Studio 這類工具，讓你在本地跑 7B 到 13B 的模型已經非常可行。這也是今天實作的目標區間。

Part 3 · 量化與 Hugging Face

什麼是量化？

原始模型用 16 位元浮點數（FP16）儲存每個參數。一個 70 億參數的模型，光參數就要約 14 GB。量化，就是把這些數字從 16 位元壓縮到 8 位元、4 位元甚至更低。

打個比方：你有一張高解析度照片，原始檔案很大。量化就像把它存成 JPEG —— 畫質稍微降一點，但檔案小很多。

8-bit

Q8

品質接近原始，但檔案還是偏大。

最推薦 · 4-bit

Q4_K_M

比 FP16 少用約 40% VRAM，品質損失不到 1%。K 是用 K-means 聚類優化量化，M 代表 Medium，是品質與壓縮率的中間值。

2-bit

Q2

極致壓縮，檔案最小，但品質損失明顯。

實務建議新手從 Q4_K_M 開始就對了。它是最廣泛使用、社群驗證最多的量化格式。

Part 3 · 量化與 Hugging Face

Hugging Face 與 GGUF 格式

Hugging Face 是 AI 界的 GitHub —— 一個模型託管平台，上面有數十萬個開源模型，支援各種格式，包括 LM Studio 使用的 GGUF。

檔案格式

GGUF 是什麼？

它是 llama.cpp 生態系使用的模型檔案格式，專門為本地推理優化。在 Hugging Face 搜尋時加上 GGUF 關鍵字，就能找到可在 LM Studio 直接使用的版本。

操作方式

怎麼找模型？

搜尋「模型名稱 + GGUF」，例如 Llama-3.1-8B-Instruct-GGUF。進入頁面後在 Files 區塊找到 .gguf 結尾的檔案，挑你要的量化版本下載。

為什麼重要模型檔通常有好幾種量化版本並列。選錯版本，不是跑不動，就是白白犧牲品質。看檔名就能認：Q4_K_M 是安全牌。

Part 4 · 進階設定

GPU、上下文長度與 Temperature

GPU Offload

GPU 卸載

控制模型有多少層跑在 GPU 上，預設 100%。VRAM 不夠可調低，但低於 50% 速度會大幅下降，因為會回退到 CPU 計算。

Context Length

上下文長度

模型能記住多少 token 的對話歷史，預設通常 4096。可調到 8192、16384 甚至更高，但上下文翻倍，VRAM 用量也翻倍。

Temperature

生成的隨機性

低溫（0.1–0.3）適合事實性問答；高溫（0.7–1.0）適合創意寫作。

n_parallel

並行請求

LM Studio 0.4.0 的新功能，允許同時處理多個推理請求，而不是排隊等待，預設 4 個並行槽位。

COSTAR：六個要素的 prompt 設計框架

C · Context

上下文

任務的背景。「我正在準備一場給大學生的 AI 入門講座」。

O · Objective

目標

要模型完成什麼。「幫我寫一段 200 字的講座開場白」。

風格

寫作風格。「用輕鬆幽默的口語風格，像在跟朋友聊天」。

語氣

情感基調。「熱情、鼓勵」。

受眾

目標讀者。「完全沒有技術背景的大一新生」。

回應格式

指定輸出。「Markdown 格式，包含標題和三個要點」。

實戰建議不需要每次都寫滿六個要素。但 C（上下文）和 O（目標）是絕對必要的，有了這兩個，輸出品質就會明顯提升。

Part 5 · 核心概念

Token 與上下文窗口

最小單位

Token 是什麼？

模型處理文字的最小單位。你可以把它想成「模型眼中的字」。

一次能看多少

上下文窗口

模型一次能「看到」的最大 token 數量。這個窗口包含你的 prompt + 模型的回應 + 所有歷史對話。

如果對話超過上下文窗口，最舊的內容會被「擠出去」，模型就看不到了。這就是為什麼長對話中，模型有時會「忘記」前面講過的東西。

實務影響LM Studio 的上下文長度設定，會直接影響你一次能餵多少資料給模型。處理長文件時，記得把上下文長度調高。

Part 5 · 核心概念

RAG：讓模型回答它沒學過的資料

RAG（Retrieval-Augmented Generation，檢索增強生成）是解決模型「不知道你的私有資料」的方法。

01

切塊

把你的文件（PDF、網頁）切成小塊。

02

轉向量

用 Embedding 模型把每一塊轉成向量。

03

存向量庫

把這些向量存進向量資料庫。

04

找相似

提問時把問題也轉成向量，找出最相似的文檔塊。

05

一起餵給 LLM

把文檔塊 + 問題一起餵進去，讓它據此回答。

Embedding 的角色就是把「語意相似度」變成可計算的數學問題 —— 兩段文字語意越接近，它們的向量距離就越近。

Part 5 · 核心概念

幻覺：模型為什麼會「一本正經地胡說」

幻覺是指模型生成看起來合理、但實際上錯誤的資訊。主要原因有三個。

原因 01

訓練目標的錯位

模型被訓練成「填補下一個最可能的詞」，而不是「說真話」。不知道答案時，它會依語言模式「猜」一個聽起來合理的答案。

原因 02

訓練資料的污染

網路上的錯誤資訊被學進去了，模型沒辦法區分「對的」和「錯的」。

原因 03

解碼策略的隨機性

Temperature 越高，模型越傾向選擇「不確定」的詞，幻覺風險也越高。

怎麼降低① 在 prompt 明確要求「如果你不確定，請說『我不知道』」　② 使用 RAG，讓模型基於真實文檔回答　③ 降低 Temperature　④ 交叉驗證模型的回答。

Part 5 · 工具調用與 MCP 預告

讓模型從「說話」變成「做事」

模型本身只能生成文字。但如果讓它能「使用工具」呢？工具調用（Tool Calling）就是讓模型在需要的時候，呼叫外部函數來完成任務。

範例
模型判斷需要查天氣 → 呼叫一個天氣 API → 把結果拿回來 → 再生成回答。

Part 6 · MCP 與工具調用

MCP 是什麼？

MCP 是 Anthropic 在 2024 年提出的通訊協議，全名 Model Context Protocol。打個比方：MCP 就像是 AI 的 USB-C 接口 —— 以前每個工具都要寫專屬連接方式，現在一次對接，到處能用。

ROLE 1

Host

你的 LLM 應用，例如 LM Studio。

ROLE 2

Client

MCP SDK，負責管理連接。

ROLE 3

Server

提供工具的服務，可以是本地進程（stdio）或遠端服務（HTTP）。

與 Function Calling 的關係不是替代，是互補。Function Calling 解決「單個模型怎麼調用自己的 API」；MCP 解決「怎麼標準化工具接口，讓多個 Agent 共享多個工具」。

Part 6 · Web Search MCP

Web Search MCP

設定一個 web search MCP server 後，你可以問模型：「今天台北的天氣如何？」模型會自動呼叫搜尋工具，然後基於搜尋結果回答。

Part 7 · 本地模型的極限與雲端的必要性

本地模型的三個硬限制

本地跑 LLM 聽起來很美好：免費、隱私、離線可用。但當你真的把它投入工作，會撞到三面牆。

硬限制 01

上下文窗口的天花板

小型本地模型在上下文從 1K 擴到 65K 時，抽取任務效能會下降 13%。更麻煩的是 KV Cache 隨上下文線性成長：21GB 模型加上上下文與開銷，實佔可能暴增到 25–30GB，一旦 VRAM 溢出到系統 RAM，不是變慢，是崩潰。

硬限制 02

運算能力的本質差距

RTX 4090 的 24GB VRAM 聽起來很多；雲端單張 H100 有 80GB，而 Google TPU 叢集是數千張晶片協同。研究指出，本地推論效能落後雲端 1.4 到 7.4 倍 —— 這不是優化能彌補的差距。

硬限制 03

模型「智商」的壓縮代價

本地跑得動的模型幾乎都量化過。frontier 模型（GPT-4o、Claude、Gemini）原始參數量是本地模型數十倍，且未經壓縮。簡單程式碼、摘要還行，複雜推理鏈與多步驟 agent 任務會明顯落後。

一句話總結本地模型是「夠用」，雲端模型是「好用」。差距不在你有沒有錢買顯卡，而在架構層面的根本不同。

雲端的必要性與混合策略

雲端不是抽象概念，它的本質是：把運算與儲存放在別人的資料中心，你透過網路存取。

  • 隱私敏感、機密資料
  • 需要離線工作的場景
  • 預算有限，不想付訂閱費
  • 實驗性專案，需要快速迭代

這些該上雲端

  • 需要最新知識的任務
  • 生產環境的關鍵工作
  • 與團隊協作、分享 AI 產出
兩種路線的取捨雲端優勢：上下文可開到 100 萬 token、模型永遠最新、按用量付費。代價：資料要離開裝置、有網路延遲、長期大量使用成本會累積。最務實的做法是混合架構，各司其職。

什麼時候用本地，什麼時候用 Gemini

你現在同時擁有本地模型（LM Studio）與雲端生態系（Gemini）的知識。最後給你一個實用的決策框架。

選本地模型

LM Studio 的情境

  • 敏感或機密資料，不希望離開電腦
  • 需要離線工作
  • 預算有限，不想付訂閱費
  • 簡單的生成、摘要、翻譯
選雲端 Gemini

Gemini 的情境

  • 超長文件（100 萬 token 等級）
  • 需要與 Gmail、Drive、Docs 深度整合
  • 需要最新模型能力與知識
  • 複雜推理與多步驟任務
混合策略兩者不是互斥。日常隱私任務交給 LM Studio，需要強大推理與生態系整合的任務交給 Gemini —— 這是最務實的做法。
